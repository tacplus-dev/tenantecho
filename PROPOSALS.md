## Open
- **<title>** (<date>, <issue/run link>): <what and why>
- **fleet-seatrials: name the target tenant in tenantecho calls** (2026-10-28, #5): since #5, `PingRequest.tenant` (2) and `PingPigeonRequest.tenant` (3) are the route fields, and a call with an empty or malformed one is refused with `INVALID_ARGUMENT` before it is sent. The seatrials client sends neither (tacplus-dev/fleet-seatrials `client/cmd/seatrials/main.go`, `ping` and `pingPigeon`). When that fleet moves to tacplus 2.5, it should send the credential's tenant tid, and maybe add a `-tenant` flag to show that a call naming another tenant is refused (`PERMISSION_DENIED`). Its `build/proto/services/tenantecho.proto` copy also has to follow this one.
- **README examples use tenant names, not tids** (2026-10-28, #5): the README and tests show `tenants/acme`. Since 2.5, a tenant's namespace is `/tenants/<tid>` (8 characters of `[0-9a-z]`), and the route field must be a tid. The examples should use a tid, so they match what a caller now sends.
- **Floor 2.6 and a pinned build image, so plain `tacplus` can run the gates** (2026-10-29, #5): tacplus-dev/tacplus#193 replaced the `tacplus:X.Y` compiler image (no `go`) with `build:X.Y`, whose `tacplus` runs the version pinned in `tacplus.lock`, but only from 2.6.0 (tacplus-dev/tacplus#213), and the launcher refuses a pin from another line. `tacplus:2.5` (2.5.1 today) still cannot generate Go. Once 2.6.0 is out: set `tacplus: "2.6"`, pin it (`tacplus pin`, `tacplus.lock`), and run the gates in `build:2.6`. The looper's `tacplus` wrapper runs `tacplus/tacplus:<floor>`, so it has nothing to run for 2.6 until tacplus-dev/looper changes (tacplus' own PROPOSALS.md; tacplus-dev/looper#15 removes the wrapper). Update 2026-11-06 (#5): plain `tacplus` 2.5.11 now generates Go, so the gates no longer need this; what is left is the pin (a reproducible compiler) and the 2.6 features (v2.6.0 is out). Update 2026-11-06 (nightly scan): the floor and the pin are now bug #9 (2.6 is the latest released line; the gates pass on 2.6.1); what is left here is using 2.6 features. Update 2026-11-07 (#9): the floor is 2.6 and `tacplus.lock` pins 2.6.1 and `build:2.6.1` by digest, so the floor and the pin are covered by #9; what is left is the 2.6 features.
- **looper-trace does not see tenantecho's handlers** (2026-11-03, #8): `looper-trace check` reports `pass (0 handlers, 0 findings)` here, before and after #8, so it misses `TenantEcho.Ping` and `PingPigeon` (`func (s *Server) X(ctx, *servicemanager.Caller, *pb.XRequest)`, the chassis' handler shape with a caller argument) and would not have caught the dropped `trace_id` #8 fixed. A change for tacplus-dev/looper: read that signature as a handler, with `internal/echo` as a test case.
- **The generated TypeScript W2S client pulls TOML and YAML parsers into a browser page** (2026-11-07, #7): `web/`'s bundle is about 310 kB (82 kB gzipped), mostly not the page: the generated `model/` imports `@iarna/toml` and `js-yaml` (config loading a browser module never uses), and Vite warns on `@iarna/toml`'s direct `eval("require('util').inspect")`. The gateway's own webapp has the same imports. A change for tacplus-dev/tacplus: keep `w2sm` and the types it needs free of the config parsers, so a contributed module bundles only its client.
- **The ping page asks for the tenant's tid** (2026-11-07, #7): `web/` cannot tell which tenants the signed-in person belongs to, so it asks for the tid and mints the call's token for `/tenants/<tid>`. If the gateway or kernel offered a W2S "my tenants" call (a W2S client of it, declared in `web/proto/clients/echoweb.proto`), the page could offer them instead.
- **A `release/0.1` branch, so v0.1.0 can take a patch** (2026-11-07, #9): v0.1.0 has the 2.5 floor, and on 2.5 generation no longer passes (`coop`'s latest release needs 2.6), so v0.1.0 cannot be built as tagged. #9 fixed it on main, but main has taken a feature since v0.1.0 (#7, the ping page), so a v0.1.1 cannot be tagged from main (tacplus `docs/VERSIONING.md`). The repository has no `release/MAJOR.MINOR` branch to backport to. Someone with the right to do so could cut `release/0.1` at v0.1.0 and protect it; then #9's commit can be backported to it as a pull request and tagged v0.1.1. The other way is to leave 0.1 alone and fix it in the next minor, v0.2.0. Update 2026-11-13 (#2): `release.yml` builds a tag without `tacplus.lock` with the pin of the workflow's commit (2.6.1 satisfies v0.1.0's 2.5 floor, and v0.1.0's Go source is main's), so v0.1.0's image is built from the tag as it is; a `release/0.1` is needed only for a real 0.1 patch.

- **Run the release scripts' tests in the gates** (2026-11-13, #2): `ci/release_test.sh` tests the image tags, notes and lock a release takes, with git alone, but the full gates the manager runs (no gates.yaml) are `tacplus && go build ./... && go vet ./... && go test ./...`, so a change to `ci/` is not tested on land unless its report names the script. A `gates.yaml` mapping `ci/**` and `.github/workflows/release.yml` to a set that includes it (and `actionlint`) would.
